# Stage 8 classifier — offline evaluation harness

This is an iteration loop for tuning the Stage 8 inbound classifier prompt.
It runs synthetic customer emails through Claude and scores the routing
decision against expected buckets. Pure offline — no email, no Airtable, no
production wiring.

## What it does

The Stage 8 classifier (see `automation-pipeline.md`) routes every inbound
customer email into one of five buckets:

| Bucket          | What it means                                                          |
| --------------- | ---------------------------------------------------------------------- |
| `INFORMATIONAL` | A question answerable from the customer record. No site change.        |
| `AUTO_HANDLE`   | A change request that is fully specified — executable as written.      |
| `CLARIFY`       | A small change request that is under-specified — needs one question.   |
| `QUOTE`         | A request matching a published priced extra (new page, integration…).  |
| `ESCALATE`      | Anything else: judgment-heavy, regulated, urgent, low-confidence.      |

Stage 8 is the load-bearing piece of our unit economics. A misclassified
`AUTO_HANDLE` becomes a customer-facing mistake on a live site. We need this
prompt tight before it sees real inbound mail.

## Files

- `classifier_prompt.md` — the system prompt sent to Claude. **Edit this to
  iterate.**
- `eval_cases.jsonl` — 35 synthetic test cases, one JSON object per line.
- `run_eval.py` — the runner. Calls Claude with each case, writes results
  to `eval_results.csv`, prints accuracy.
- `eval_results.csv` — generated by `run_eval.py`. Overwritten each run.

## Run it

From the project root (where `.env` lives):

```bash
set -a; source .env; set +a && python3 scripts/stage8/classifier-eval/run_eval.py
```

This will run all 35 cases, write `eval_results.csv`, and print a per-bucket
accuracy summary plus a list of mismatches with their reasoning.

### Faster iteration

Smoke test on the first 5 cases:

```bash
set -a; source .env; set +a && python3 scripts/stage8/classifier-eval/run_eval.py --limit 5
```

Re-run a single case (useful after editing a prompt to debug one regression):

```bash
set -a; source .env; set +a && python3 scripts/stage8/classifier-eval/run_eval.py --case-id ESC_03
```

Try a different model:

```bash
set -a; source .env; set +a && python3 scripts/stage8/classifier-eval/run_eval.py --model claude-opus-4-7
```

## How to iterate

1. Run the eval. Inspect mismatches in `eval_results.csv` and the printed
   reasoning.
2. Edit `classifier_prompt.md` — sharpen a bucket definition, add a
   smells-weird signal, tune the escalate bias.
3. Rerun. Compare which mismatches resolved and which appeared. A
   non-regression diff is more important than the absolute number.
4. If a mismatch is the **case's** fault (the expected bucket is debatable),
   edit the case or its `notes` field. Document the call.
5. When you're happy, commit the prompt + cases together so the iteration
   history shows up in `git log`.

The prompt is the artifact under test. The cases are the test set. The
script is plumbing; touch it only when the contract changes.

## Where this graduates

The prompt in `classifier_prompt.md` lives here until the Stage 8 inbound
worker is built. Per `automation-pipeline.md` (Tooling stack, "Update
classifier"), the production worker will use **Claude API with structured
outputs** behind an email-webhook receiver — exactly the tool-use shape
this harness already exercises. When that worker is built, it should
import the same prompt file (or be wired to read from this repo) so prompt
edits land in one place. The test cases here become the regression suite
for that worker.

## Dependencies

Zero pip installs. Stdlib only (`urllib`, `json`, `csv`, `argparse`).
Matches the style of `scripts/generate_briefs.py` and `scripts/pull_leads.py`.

## What this harness does NOT do

- Does not parse real email (no IMAP, no Postmark, no Resend webhook).
- Does not write to Airtable.
- Does not send any reply to anyone.
- Does not deploy anything.
- Does not exercise the preview-and-confirm flow.

Those belong in the production Stage 8 worker, not in a prompt-tuning loop.
